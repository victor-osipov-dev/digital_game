# Digital Game

Rummikub-подобная игра на Godot 4.7 с сетевым режимом на двух VPS.
Клиент — Godot, сервер — Node.js. Серверы **авторитетны**: они держат партию,
проверяют каждый ход и никогда не показывают игроку чужую руку.

Этот файл — единственный, который нужно прочитать целиком, чтобы понять проект
и продолжить работу. Остальное в репозитории — код, и он объясняет себя сам.

## 1. Что это

**Правила.** Rummikub с полным набором из двух колод: 108 фишек =
4 цвета × 13 значений × 2 колоды + 4 джокера. Ряд — от 3 фишек:
либо серия одного цвета по возрастанию, либо набор одного значения разных
цветов. Джокер подставляет любую недостающую фишку. Первым ходом нужно
выложить не меньше 30 очков (настройка комнаты). Мест за столом 2–5,
по 14 фишек на игрока.

**Два режима.**

* **Одиночный** — 2–5 игроков, остальные места занимают боты четырёх
  уровней сложности. Есть подсказки, отмена хода, перестановка на столе.
* **Сетевой** — партия на сервере: минимум двое живых, пустые места
  добирают серверные боты. Партия стартует сама, когда комната заполняется,
  или по таймеру ~минуты, если живых уже двое. У каждого хода — видимый
  всем обратный отсчёт; время вышло — сервер сам берёт фишку из колоды и
  передаёт очередь дальше. На место выбывшего бот
  ставится только тогда, когда живых остаётся двое и больше; остался
  один — партия встаёт на паузу («ждём второго»), место ушедшего
  освобождается для нового игрока, а боты в это время молчат. Ушёл и
  последний живой — комната удаляется. Комната живёт на одном сервере,
  и вся партия проходит на нём же.

**Серверы сейчас:**

| id | Имя | Адрес | Порт |
|---|---|---|---|
| `srv-ru` | Россия | `85.209.2.116` | 6767 |
| `srv-lv` | Латвия | `31.56.196.114` | 6767 |

## 2. Быстрый старт

### Клиент

Нужен Godot **4.7.2-stable** (или новее той же мажорной версии).

```
godot --path . --import      # один раз: регистрирует импорт ресурсов
godot --path .
```

Игра запустится в главное меню. Кнопка «Играть по сети» открывает сетевое
меню: вход, список комнат с **обоих** серверов, ожидание игроков.

> `--import` нужен после первого добавления нового скрипта с `class_name`.
> Без него движок запустит не тот файл, и тест выглядит «запустился, но
> выдал чужой вывод».

### Серверы уже развёрнуты

Оба VPS работают, слушают `0.0.0.0:6767`, отвечают на настоящее
WSS-рукопожатие с закреплённым сертификатом. Проверить прямо сейчас:

```bash
node server/tools/deploy_check.js
```

Финальная строка должна быть `КЛАСТЕР РАБОТАЕТ: ...`.

### Если серверы нужно развернуть с нуля

См. [Развёртывание серверов](#12-развёртывание-серверов).

## 3. Архитектура

```
                    ┌──────────────────────────┐
   игрок 1 ────────▶│                          │
   (Godot)          │   игровой сервер (Node)  │◀──── партия в памяти
                    │   WSS :6767, авторитет   │
   игрок 2 ────────▶│                          │
   (Godot)          └───────────┬──────────────┘
                                │  раз в минуту, подписанный gossip
                    ┌───────────▼──────────────┐
                    │  игровой сервер (Node)   │◀──── партия в памяти
   игрок 3 ────────▶│  WSS :6767, авторитет    │
   (Godot)          └──────────────────────────┘
```

### Главные решения

**Никакого P2P.** Весь обмен идёт через сервер. Клиент не знает адресов
других игроков и не может с ними соединиться.

**Партии не реплицируются.** У каждого сервера своя правда о своих партиях.
Если сервер умер — партии на нём потеряны, и это осознанно: синхронизировать
состояние партии между серверами дороже, чем её потерять. Игроки, у которых
уже идёт партия, **не переключаются** на другой сервер.

**Аккаунты реплицируются.** Завели аккаунт на России — заходите на Латвии
тем же логином. Это единственное, что ездит между серверами, плюс реестр
серверов. Всё остальное (комнаты, партии, сессии) живёт на своём сервере.

**Сессии общие, но не хранятся в базе соседа.** Токен сессии — не запись в
таблице, а **HMAC-подпись** общим секретом кластера. Поэтому любой сервер
кластера её проверяет сам, без похода к соседу. См. [раздел 9](#9-аккаунты-сессии-пароли).

**Нет nginx.** На 443 обеих машин уже работает чужое продакшен-приложение
(`ai-box-cars.ru` с LE-сертификатом, x-ui/xray). Мы его не трогаем:
Node.js сам занимает свободный порт **6767** и сам говорит TLS.

**Доменов нет.** Адреса серверов — голые IP, публичного CA для них не
существует. Сертификат самоподписанный и **зашит в клиент**: клиент требует,
чтобы сервер предъявил именно его, побайтово. Подменить сервер посередине
нельзя, а отключить проверку в коде негде. См. [раздел 10](#10-tls-и-сертификаты).

**Один порт на всё.** HTTP, WebSocket и TLS — один процесс, один порт 6767.

**Партия в памяти.** Игровое состояние не пишется в SQLite. Оно гибнет
вместе с процессом. В базе только аккаунты, курсоры репликации, реестр
серверов и хеши сессий.

## 4. Клиент: слои и файлы

```
scenes/
  main_menu.tscn      Control на весь экран, всё меню строится кодом
  game.tscn           партия
scripts/
  core/
    settings.gd       автозагрузка: язык, масштаб шрифта, настройки
    rules.gd          ★ правила — эталонная реализация
    deck.gd           колода, раздача, тайл
    tile.gd           одна фишка (id, цвет, значение, джокер)
    game_state.gd     состояние партии С ТОЧКИ ЗРЕНИЯ ИГРОКА
    turn_planner.gd   боты: подбор хода по сложности
  net/
    net.gd            автозагрузка: сокет, запросы, автопереподключение
    protocol.gd       ★ зеркало server/src/protocol.js
    servers.gd        список серверов, проверка связи, список комнат
    session.gd        токен сессии, user://session.json
    certs.gd          зашитые сертификаты, TLSOptions
    view_builder.gd   сборка представления партии из ответа сервера
  ui/
    main_menu.gd      главное меню, одиночная игра, настройки
    online_lobby.gd   сетевое меню
    game.gd           сцена партии
    tile_view.gd, row_block.gd, flow_tiles.gd, drop_layer.gd
                       элементы интерфейса партии
```

### Ключевое: `GameState` — это то, что сервер разрешил показать

`scripts/core/game_state.gd` **не** симулирует игру. Это разбор присланного
сервером снимка. Отсюда:

* `hand_seat()` — чья рука приехала (у каждого игрока своя);
* `my_turn()` — чей сейчас ход;
* `hand_count_override`, `deck_count_override` — у соперников рук не видно,
  известны только **числа** фишек;
* `connected` — кто на связи, влияет на показ «отвалился».

То есть подделать сопернику чужую руку на клиенте физически нечего:
её нет в данных. А проверку всё равно делает сервер.

### `ViewBuilder` отдаёт общие объекты

`view_builder.gd` кэширует `Tile` **по id** и отдаёт один и тот же объект
на все руки. `GameState` сравнивает фишки по ссылке, а не по значению.
Если это сломать, начнут «исчезать» фишки, взятые в ход.

### JSON от Godot — это `float`

Парсер Godot возвращает **все** числа как `float`. Любое числовое поле из
сети читается через `int(...)`. Забытый `int()` даёт не ошибку компиляции,
а тихую поломку сравнений и индексов.

### Нули на границе сети

`NetProtocol.clean()` и `NetProtocol.parse()` **один раз** выкидывают ключи
со значением `null` (в массивах `null` заменяется на `""`). Сделано на границе,
чтобы ни одна строчка дальше по коду не проверяла `null`.

Осторожно: `Dictionary.get(key, default)` возвращает `null`, если ключ
**есть** и его значение — `null`. Значение по умолчанию **не подставляется**.
А `String(null)` — ошибка в рантайме.

## 5. Сервер: слои и файлы

```
server/
  src/
    index.js         вход: читает конфиг, поднимает HTTP+WS+TLS
    config.js        разбор server.env в объект с разумными умолчаниями
    hub.js           протокол: маршрутизация сообщений, auth, владение местом
    rooms.js         комнаты, места, очередь быстрого матча, отключения
    accounts.js      регистрация, вход, пароли, репликация
    cluster.js       gossip раз в минуту, слияние, реестр
    views.js         проекция партии под конкретного игрока
    db.js            схема и запросы
    sqlite.js        тонкая обёртка над встроенным node:sqlite
    log.js
    protocol.js      ★ контракт; зеркалится в scripts/net/protocol.gd
    engine/
      rules.js       ★ правила — порт rules.gd
      catalog.js     108 фишек
      deck.js        тасовка и раздача
      game_state.js  ★ состояние партии на сервере (полное)
  tools/             тесты и инструменты
  deploy/            deploy.py, systemd-юнит, скрипты сертификатов
```

### Зависимости

Ровно один пакет — **`ws`**. Всё остальное стандартно: `node:sqlite`
(встроен с Node 22+, в v24 стабилен), `node:crypto`, `node:https`.

`sqlite.js` — небольшая обёртка, повторяющая нужное подмножество
(`node:sqlite` умеет только позиционные `?`). Написана вручную, чтобы
не тянуть нативный `better-sqlite3`, который требует сборки.

### Требования к Node

Нужен **Node ≥ 22** (ради `node:sqlite`). Ubuntu 24.04 из коробки даёт
node 18, поэтому деплой ставит официальный статический тарбол в `/opt/node`,
сверяя SHA256 из `NODE_SHA` в `deploy.py`.

Зафиксировано: `v24.21.0`,
SHA256 `fd8e59d5a511510f6a298afb548f18c7d2b1be404d8b4a27d94fbe49f56cb2d6`.

### Пути на сервере

| Что | Где |
|---|---|
| Программа | `/opt/digital-game` |
| Конфиг и секреты | `/etc/digital-game` (`server.env`, права `0640`) |
| TLS | `/etc/digital-game/tls/` |
| Данные (SQLite) | `/var/lib/digital-game` |
| Node.js | `/opt/node` |
| Юнит | `/etc/systemd/system/digital-game.service` |

### Как сервер устроен внутри

* **`hub.js`** — разбор сообщений. Держит контексты сокетов, решает, кто
  что может. Отвечает на запросы, рассылает события.
* **`rooms.js`** — комнаты и места. Место принадлежит **игроку**, а не
  сокету; при переподключении место переиспользуется.
* **`views.js`** — превращает полное состояние в то, что **можно** показать
  конкретному игроку. Рука соперника сюда не попадает по построению.
* **`engine/game_state.js`** — вся правда о партии, со всеми руками.

### Сокет и место: `claimSeat`

Место за столом принаджит игроку, но обработчик закрытия привязан к сокету.
`Hub.claimSeat(room, seat, socket)` помечает прежнего владельца как
`superseded` и закрывает его с кодом **4001** («выполнен вход в другом окне»).
Обработчик закрытия для `superseded` выходит сразу.

Клиент на 4001 **не переподключается** (`Net.CLOSE_REPLACED`). Иначе две
вкладки вытесняли бы друг друга по кругу.

Это чинит реальный класс поломок: раньше переподключение после обрыва
перехватывало сокет у игрока в лобби, а закрытие «одноразовой» с��зи
освобождало место, и `_maybeCloseLobby` **удалял комнату**.

## 6. Протокол

Транспорт — один WebSocket, каждое сообщение — JSON-объект с полем `t`.

**`protocol.js` (сервер) и `protocol.gd` (клиент) — зеркала.** Меняете в
одном — меняйте в другом, иначе клиент перестанет понимать ответы.
Тест `test_parse.gd` ловит расхождение на этапе загрузки скриптов.

### Клиент → сервер

| Тип | Данные | Ответ |
|---|---|---|
| `auth.register` | `{login, password, nick}` | `auth.ok` |
| `auth.login` | `{login, password}` | `auth.ok` |
| `auth.resume` | `{token}` | `auth.ok` |
| `lobby.open` | `{token}` | `auth.ok` — **наблюдатель**, только чтение |
| `auth.logout` | `{}` | — |
| `auth.password` | `{old, new}` | `auth.ok` |
| `auth.nick` | `{nick}` | `auth.ok` |
| `servers.list` | `{}` | `servers.list` |
| `rooms.list` | `{}` | `rooms.list` |
| `room.create` | `{seats, require30, name, password}` | `room.state` |
| `room.join` | `{code, password}` | `room.state` \| `game.state` |
| `room.leave` | `{}` | `room.left` |
| `room.start` | `{}` | `room.state` \| `game.state` |
| `room.chat` | `{text}` | *зарезервировано* |
| `quick.join` | `{seats, require30}` | `quick.state` \| `room.state` |
| `quick.leave` | `{}` | `quick.state` |
| `game.commit` | `{ops:[...]}` | `game.state` \| `game.error` |
| `game.draw` | `{}` | `game.state` \| `game.error` |
| `game.skip` | `{}` | `game.state` \| `game.error` |
| `game.rejoin` | `{}` | `game.state` |
| `game.peek` | `{tile, kind, row?, index?, at?}` | — (рассылка соперникам) |
| `game.draft` | `{rows:[{id, tiles:[...]}, ...]}` | — (рассылка соперникам) |
| `ping` | `{}` | `pong` |

### Сервер → клиент

`hello` (каталог фишек, время удержания места), `auth.ok`, `auth.err`,
`servers.list`, `rooms.list`, `room.state`, `room.left`, `quick.state`,
`game.state`, `game.error`, `game.peek`, `game.draft`, `toast`, `pong`.

Конверт `game.state` — `{state, grace, paused, waiting}`: `grace` —
сколько секунд ещё ждём переподключение этого игрока, `paused` — ждём
кого-то из сидящих, `waiting` — живых остался один и партия ждёт второго
(в этом состоянии никто не ходит и боты молчат). В `state.turnLeft` —
секунды до конца текущего хода; `null`, когда отсчёта нет (пауза,
ожидание, конец партии).

### `rid` — обязательное поле-коррелятор

Клиент кладёт в каждый запрос строку `rid` и по ней узнаёт **свой** ответ.
Без этого не отличить «мой ход отклонили» от «соперник что-то сделал»:
события приходят одним и тем же типом сообщения.

**В рассылках `rid` не проставляется.** Клиент обязан применять чужое
состояние вслепую и не выдавать его за результат своего хода.

`request()` в `net.gd` возвращает **первое** сообщение с нашим `rid`.
Он **никогда не виснет**: без связи вернёт `{"t":"offline"}`, при молчании
сервера — `{"t":"timeout"}`.

### `lobby.open` — наблюдатель

Клиенту нужно прочитать список комнат с чужого сервера, но у него одна
связь, и та занята. Обычный `auth.resume` для этого не годится: он
перехватывает сокет игрока, и закрытие «одноразовой» связи выбивает его
из комнаты.

`lobby.open` проверяет токен, ставит `ctx.observer = true` и отказывает
всем командам кроме `rooms.list`, `servers.list`, `ping`. Обработчик
закрытия для наблюдателя выходит сразу — выброшенная связь чтения не может
задеть состояние комнат.

### `game.commit`: клиент присылает готовый стол

Не «я взял фишку 42», а **итоговый стол целиком**:

```json
{"t":"game.commit","ops":[{"op":"set_table","rows":[
  {"id":0,  "tiles":[3,17,29]},
  {"id":7,  "tiles":[40,41,42]}
]}]}
```

* `id > 0` — существующий ряд, `0` — новый;
* `set_table` обязан быть **единственной** операцией;
* таблица присылается **полностью**, не дельтой.

**Порядок фишек внутри ряда сервер не навязывает.** `canonicalOrder` в
`engine/game_state.js` сначала пробует порядок как прислали (если ряд
валиден — он и есть), иначе перебирает циклические сдвиги, иначе сортирует
с джокерами в каждом промежутке. Без этого легальная перестановка на столе
отклонялась на `endTurn`.

### Таймер хода

Ход ограничен по времени: `DG_TURN_SECONDS`, по умолчанию 60 секунд.
Дедлайн живёт в комнате (`room.turnDeadlineMs`, чей — `room.turnDeadlineFor`),
ставится и гасится хабом в `maybeRunBots` → `_scheduleTurn` и сбрасывается
при каждом завершённом ходе. Секунды до конца хода уходят всем в
`state.turnLeft` поля `game.state`; пауза, ожидание второго игрока и конец
партии гасят отсчёт (`turnLeft: null`).

Когда время вышло, сервер сам ходит за игрока: берёт фишку из колоды (на
пустой колоде пропускает ход), передаёт очередь дальше и шлёт тому, чьё
время кончилось, `toast` «Время хода вышло…». Партия не встаёт, даже если
игрок отвлёкся. Просроченный таймер в паузе/ожидании ничего не делает.

**Боты ждут людей.** В сетевой комнате боты ходят только при двух и более
живых за столом (`humanCount >= 2`) — при одном живом они молчат, а отсчёт
хода у оставшегося человека продолжается. Это вторая линия защиты рядом с
флагом `waiting` («ждём второго»), который тоже гасит и ботов, и отсчёт.

### `game.peek` — превью хода соперника

Когда игрок перебирает варианты (ставить/убирать фишку), клиент шлёт

```json
{"t":"game.peek","tile":7,"kind":"into","row":3,"index":2}
```

Сервер **правила не проверяет** — это картинка: валидируется только форма
(целые числа, `tile` из каталога, `kind` из белого списка), после чего
сообщение уходит остальным сидам как `{"t":"game.peek","from":0,...}`;
автору своё превью не возвращается. Ретрансляция с троттлингом 40 мс на
сид, чтобы дешёвый клиент не сыпал превью пачками; сам `clear` идёт мимо
окна — при смене цели он уходит вплотную к последнему превью, и потерянный
`clear` оставил бы призрак висеть до собственного протухания.

Виды: `into` — в существующий ряд `row` на позицию `index`; `new` — новый
ряд на позицию-разрыв `at`; `back` — забирает в руку; `clear` — убрать
призрак. Фишку клиент рисует по своему каталогу из `hello` — наружу уходит
только номер, подделать цвет или значение нельзя. У `new` наблюдатель
**врезает в стол ряд той же высоты** и ставит призрак в разрыв: видно, что
игрок открывает новый ряд, а не кладёт фишку поверх соседней карточки.

### `game.draft` — черновик стола соперника

Выкладка у автора **локальная**: стол уходит на сервер только целиком, в
`game.commit`. Без дополнительного канала соперники не видели бы ничего,
пока игрок раскладывает, — поэтому после каждого локального изменения
клиент шлёт **весь свой стол**:

```json
{"t":"game.draft","rows":[
  {"id":1, "tiles":[3,17,29]},
  {"id":5, "tiles":[40]}
]}
```

Формат `rows` совпадает с `set_table` у `game.commit`, но `id` рядов
уходят **локальные, без обнуления новых** — по ним же соперник рисует
призрак `game.peek` в только что созданный ряд. Сервер, как и с `peek`,
правила не проверяет: валидируется форма (≤64 рядов, ≤200 фишек, id и
tiles — целые из каталога), ретранслируется остальным сидам с троттлингом
40 мс **только от текущего игрока** (черновик не в свой ход соврал бы про
стол), автору не возвращается.

Клиент-наблюдатель рисует присланный стол **вместо** базового, причём
фишки, которых нет в серверном `state.table`, показываются **серыми** —
«лежит, но ещё не факт». Серые **накапливаются весь ход**: черновик
переживает промежуточные `game.state` (реждойн, пауза, обновление
отсчёта), пока ход его автора не кончился, — при каждом таком состоянии
серые пересчитываются по новой базе. Гасится черновик только при смене
хода, конце партии и через 15 с молчания автора; сам автор повторяет
отправку каждые 3 с, пока ход не завершён, — поэтому вошедший посреди
хода и игрок с потерянным пакетом тоже увидят раскладку.

У **автора** есть своя защита: рассылка `game.state` посреди хода (пауза
из-за обрыва соперника, его возврат, реджойн) приходит и ему, и раньше
стирала локальную раскладку вместе с повторами черновика — соперник
видел серые ровно до истечения 15 с. Теперь клиент сверяет серверный
стол с последним серверным же состоянием: не изменился — локальные
правки возвращаются поверх нового вида (`GameState.keep_local_turn_from`),
и повторы продолжаются; изменился — побеждает сервер, как и раньше.

## 7. Правила игры и почему их два

Правила написаны **дважды**: `scripts/core/rules.gd` и
`server/src/engine/rules.js`. Это сознательный дубликат — клиенту нужны
правила для подсказок и ботов, серверу для проверки, а общей кодовой базы
у Godot и Node нет.

**Расхождение запрещено** и проверяется тестом: корпус из **11 800** случаев
(генерируется `tools/gen_corpus.js`) прогоняется через обе реализации, и
вердикты обязаны совпасть. Расхождение = провал сборки.

```bash
node server/tools/run_tests.js        # проверка порта + корпус
```

Константы правил: `MIN_TILES=3`, `MAX_SET=4`, значения 1–13,
`OPENING_POINTS=30`, цвета `RED=0 BLUE=1 BLACK=2 ORANGE=3`.

**Право решает сервер.** Клиентская проверка — это подсказка и отсев
заведомо мусорного; финальное слово всегда за `rules.js` на сервере.

## 8. Кластер: что реплицируется, а что нет

| Данные | Реплицируются? | Куда |
|---|---|---|
| Аккаунты (логин, ник, хеш пароля, статистика) | **да** | соседям раз в минуту |
| Реестр серверов | **да** | соседям раз в минуту |
| Комнаты, партии, руки | **нет** | только свой сервер |
| Сессии | **не копируются** | токен самодостаточен, см. ниже |

### Как устроен gossip

Раз в `DG_GOSSIP_INTERVAL_MS` (60 с) сервер отправляет соседям подписанный
снимок. Сосед отвечает, что у него изменилось после курсора, и получает
наше. Курсоры соседей лежат в `peer_state`, журнал исходящих — в `outbox`.

Рекорд сервера исчезает, если сосед молчит дольше `DG_SERVER_TTL_MS`.
Поэтому TTL заметно больше интервала, иначе живой сервер «мигает» в списке
при просадке сети.

Требование задумано так: **добавили сервер — он появился везде в течение
минуты; убрали — запись исчезла везде**.

### Конфликты аккаунтов

* **Кто первый записал — тот и прав** (`first-write-wins`).
* Содержимое принимается **только от владельца**: запись обновляется, если
  `origin` приславшего совпадает с текущим. Сосед не может «сбросить» пароль.
* Слияние — строгим сравнением `updated_ms`. Ничьи решаются в пользу
  большего времени.

### Как устроен список комнат с двух серверов

У клиента **одна** связь, а комнаты на всех серверах. Поэтому
`Servers.list_rooms(token)` открывает отдельную короткую связь
**к каждому** живому серверу, спрашивает `lobby.open` → `rooms.list`,
сливает результат и помечает каждую комнату `server` / `serverName`.
Серверы, не ответившие, попадают в `failedServers` и показываются игроку
отдельной строкой.

Это автомат из двух фаз (`PH_SEND_RESUME` → `PH_SEND_LIST`), потому что
`rooms.list` требует авторизации.

**При создании комнаты** клиент **случайно** выбирает сервер — так комнаты
распределяются по обеим машинам.

## 9. Аккаунты, сессии, пароли

### Пароли

`scrypt`. В базе лежит строка `<salt_b64>$<hash_b64>`. Секрета, которым
сравнивают, на сервере нет — только соль и хеш.

### Сессия — не запись в базе

Токен сессии — **HMAC-подпись** общим секретом кластера
(`DG_CLUSTER_SECRET`), внутри которой зашит `updated_ms` под именем `u`.
Секрет одинаков на всех серверах, поэтому:

* любой сервер кластера проверяет токен **сам**, без обращения к соседу;
* `resume()` применяет токен, только если `u >= account.updated_ms`
  (то есть аккаунт не менялся после выдачи токена);
* смена пароля на одном сервере **инвалидирует** токены, выданные до неё,
  на всех серверах.

Секрет, разный у клиента и сервера, означает, что клиент не может подделать
ни вход, ни ход. **Держите его в `.env`, он не коммитится.**

### `auth.password` без интерфейса

Протокол, сервер и `Net.change_password()` есть, кнопки в меню — **нет**.
См. [Что делать дальше](#17-что-делать-дальше).

## 10. TLS и сертификаты

Самоподписанный сертификат на голый IP. Клиент **зашивает** его и сверяет
побайтово. Никакого «отключить проверку» в коде нет и быть не может.

### Расширение `.crt` — не украшение

Только `.crt` движок считает нативным ресурсом: он проходит через импорт и
**гарантированно** попадает внутрь PCK собранной игры. Файл `.pem` мимо
импорта проходит, и без include-фильтра в пресете экспорта клиент уедет без
сертификатов и молча не сможет подключиться.

Поэтому в репозитории лежат:

```
certs/85-209-2-116.crt     # Россия
certs/31-56-196-114.crt    # Латвия
```

> **Перевыпуск сертификата на сервере без обновления клиента = потеря связи
> с этим сервером у всех, кто ещё не обновился.** Файлы коммитятся и меняются
> только вместе с клиентом.

### Проверка связи — настоящее рукопожатие

`Servers.probe()` не «пингует порт»: он делает полное WSS-рукопожатие
с `hello` и **закреплённым** сертификатом. Так проверка ловит ровно то,
что сломается у игрока: «порт открыт» ничего не говорит о том, что
сертификат не тот или TLS не настроен.

Проверка идёт **только когда нужен список комнат**. Пока игра идёт, она не
тратит трафик.

## 12. Развёртывание серверов

### Что нужно

* Два VPS с Ubuntu 24.04, доступ по SSH от root, **без Docker**;
* `openssl`, `xz` (если их нет — `deploy.py` доставит через `apt-get`);
* `python3`, `node` на **локальной** машине (только для инструментов).

> Скрипт **не трогает** соседние сервисы: не чистит диск, не создаёт
> swapfile, не удаляет ничего вне `/opt/digital-game`. `apt-get` вызывается
> только когда действительно не хватает `openssl`/`xz`.

### Шаги

**1. Заполнить `.env`.** Скопировать `.env.example` в `.env` (в git он не
попадает) и записать:

```bash
RU_HOST=...  RU_USER=root  RU_PASSWORD=...
LV_HOST=...  LV_USER=root  LV_PASSWORD=...
DG_CLUSTER_SECRET=<32 случайных байта>
DG_RU_SERVER_ID=srv-ru     DG_RU_SERVER_NAME=Россия  DG_RU_REGION=ru  DG_RU_PUBLIC_HOST=<ip>
DG_LV_SERVER_ID=srv-lv     DG_LV_SERVER_NAME=Латвия  DG_LV_REGION=lv  DG_LV_PUBLIC_HOST=<ip>
```

Секрет генерируется так:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"
```

**Секрет обязан совпадать на обоих серверах** — именно он делает их одним
кластером. Разный секрет означает, что аккаунты не реплицируются, а токены
не переходят между серверами.

**2. Развернуть.**

```bash
python server/deploy/deploy.py              # оба сервера
python server/deploy/deploy.py ru           # только Россия
python server/deploy/deploy.py lv           # только Латвия
```

Скрипт на каждом сервере: ставит Node в `/opt/node` (сверяя SHA256),
заводит пользователя `digital-game`, кладёт программу в `/opt/digital-game`,
пишет `server.env` (права `0640`, владелец `digital-game:root`),
выпускает TLS-сертификат, ставит systemd-юнит, делает `systemctl daemon-reload`,
включает и запускает сервис, затем **ждёт готовности**.

**3. Забрать сертификаты в клиент.** Клиент без них не подключится.

```bash
python server/deploy/deploy.py --certs-only    # забрать
python server/deploy/deploy.py --certs-only --force   # перезаписать
```

Файлы обновятся в `certs/`. Их надо **закоммитить вместе с кодом клиента**.

**4. Проверить кластер.**

```bash
node server/tools/deploy_check.js              # живые серверы
python server/deploy/deploy.py --check         # то же через deploy.py
```

### Полезные флаги

| Команда | Что делает |
|---|---|
| `--status` | ничего не ставит, только показывает состояние |
| `--check` | проверка кластера с закреплёнными сертификатами |
| `--certs-only` | только забрать сертификаты в клиент |
| `--force` | перезаписать сертификаты принудительно |

### Ключи `server.env` на сервере

Образец: `server/deploy/server.env.example`.

| Ключ | Смысл | По умолчанию |
|---|---|---|
| `DG_SERVER_ID` | идентификатор себя | — |
| `DG_PUBLIC_HOST` / `DG_PUBLIC_PORT` | как видят клиенты | — |
| `DG_LISTEN_HOST` / `DG_LISTEN_PORT` | как слушаем | `0.0.0.0:6767` |
| `DG_TLS_CERT` / `DG_TLS_KEY` | пути к сертификату и ключу | — |
| `DG_CLUSTER_SECRET` | **одинаковый на всех** | — |
| `DG_PEER_URLS` | соседи через запятую | — |
| `DG_GOSSIP_INTERVAL_MS` | как часто объявляемся | `60000` |
| `DG_SERVER_TTL_MS` | после скольких молчаний исчезаем | `150000` |
| `DG_DISCONNECT_GRACE_MS` | сколько держим место отвалившегося | `90000` |
| `DG_TURN_SECONDS` | длина хода, секунд (авто-взятие по истечении) | `60` |
| `DG_ROOM_IDLE_TTL_MS` | сколько живёт пустая комната | `600000` |
| `DG_QUICK_MATCH_WAIT_MS` | ожидание очереди быстрого матча | `60000` |
| `DG_PING_INTERVAL_MS` / `DG_PONG_TIMEOUT_MS` | контроль связи | `25000` / `20000` |
| `DG_HEALTH_TIMEOUT_MS` | таймаут проверки сервера | `2500` |
| `DG_DATA_DIR` | где база | `/var/lib/digital-game` |
| `DG_LOG_LEVEL` | `info` / `debug` | `info` |

> **Плохая настройка TLS — это падение при старте, а не тихий откат на
> открытый текст.** Если сертификат не читается или не сходится, процесс
> не поднимается. Молчаливое «подключились без шифрования» хуже всего:
> его заметят игроки и не заметит разработчик.

### Диагностика

```bash
python server/deploy/deploy.py --status
node server/deploy/diag.py        # подробности по серверам
node server/deploy/recon.py       # что вообще на машине
journalctl -u digital-game -n 100 --no-pager
```

## 13. Добавление или замена сервера

### Добавить третий

1. Поднять VPS, открыть порт `6767`.
2. Добавить в `.env` блок `DG_<КОД>_SERVER_ID / _NAME / _REGION / _PUBLIC_HOST`.
3. Поправить `build_targets()` в `deploy.py` — он строит список целей из `.env`.
4. В `server.env` каждого **существующего** сервера дописать нового соседа
   в `DG_PEER_URLS`. Забытый сосед — самая частая причина «сервер не появился».
5. `python server/deploy/deploy.py`
6. `python server/deploy/deploy.py --certs-only` и **закоммитить** новый `.crt`.
7. Дописать сервер в `Servers.BUILTIN` в `scripts/net/servers.gd`
   (или просто дать клиенту узнать его через gossip — но встроенный список
   нужен, чтобы клиент вообще знал, куда стучаться в первый раз).

Через минуту после этого сервер появится в списках на всех машинах сам.

### Убрать сервер

1. Удалить соседа из `DG_PEER_URLS` на остальных и остановить сервис
   на самой машине.
2. Через `DG_SERVER_TTL_MS` запись исчезнет из реестров сама.
3. Убрать из `Servers.BUILTIN` и выпустить клиента — иначе он будет
   пытаться подключиться и получать «нет связи».

### Список серверов у клиента

`Servers.BUILTIN` — вшитый список «на старте». При каждом запуске он
сливается с `user://servers.json` по `id`: **встроенный побеждает** при
конфликте, лишние записи из файла сохраняются. То есть добавленный на
стороне сервера сервер переживёт обновление клиента, а зашитый не даст
файлу его испортить.

## 14. Настройка клиента

### Файлы в `user://`

| Файл | Что |
|---|---|
| `servers.json` | список серверов (источник правды в рантайме) |
| `session.json` | токен сессии, логин, ник |

`session.json` вынесен в **отдельный** файл намеренно: токен и список
серверов пишутся в разные моменты, и смешивать их в одном файле — значит
терять одно при записи другого.

### `Scripts`-скрипты (в редакторе: `Файл → Запустить`)

| Что | Путь |
|---|---|
| Проверка вёрстки | `res://tests/check_layout.gd` |
| Сверка API с версией движка | `res://tests/check_api.gd` |
| Сквозная проверка по живым серверам | `res://tests/test_online.gd` |

`check_layout.gd` меряет **каждый** `Control` при настоящем размере окна
576×1024 и отдельно отмечает нули. Он существует потому, что пустой экран
уже случался: `CenterContainer` отдаёт ребёнку ровно его минимальный
размер, а у прокручиваемого `ScrollContainer` минимум по вертикали — ноль.
Контент на 441 px обрезался по высоте 0, и оставался только фон.

**Разметку не подгоняют вручную.** Размеры считает движок. Ручная
подгонка (`custom_minimum_size` по вьюпорту) — это то, что забывают
переписать, когда содержимое меняется.

### Правила, касающиеся самих тестов

Эти ошибки уже стоили времени, повторять не надо:

* **Ноль проверок — это провал, а не успех.** `test_online` при недоступном
  кластере обязан падать. Раньше он печатал «ПРОЙДЕНА: 0 проверок» и выходил
  с кодом 0 — то есть тихо считал бы успехом мёртвый кластер, и первое
  настоящее падение пропустил бы.
* **Тест, который не запустился, не зелёный.** Хелпер прогоня обязан
  отличать «тест прошёл» от «Godot не стартовал и написал
  “Invalid project path”».
* **Godot в `--script` не видит автозагрузки на этапе компиляции.**
  Ждите один `process_frame`, потом берите `root.get_node_or_null("Net")`.
  Результат с `:=` по методу автозагрузки выводить нельзя — нужен явный тип.
* **`--headless --script` вешается навсегда**, если скрипт упал до `quit()`.
  Читайте перенаправленный вывод.
* **PowerShell портит кириллицу** — перенаправляйте через `cmd /c ... > file`
  и читайте `node -e` с `readFileSync(..., 'utf8')`. И не пишите `node -e`
  в двойных кавычках: PowerShell развернёт `$var`.
* **Не переписывайте исходники через `Get-Content`/`Set-Content`** —
  только инструменты редактирования.
* Имена с `NUL`, `CON`, `PRN` нельзя использовать для файлов в Windows:
  перенаправление молча не создаст файл.

## 16. Грабли и нюансы

Собрано то, что уже стоило времени. Не повторять.

### Сеть и синхронизация

* **`connect_to_url` асинхронен.** `send_text` до `STATE_OPEN` молча
  теряется. Запросы отправляются **изнутри** цикла опроса.
* **Сокет открыт ≠ сервер готов.** Между `STATE_OPEN` и приходом `hello`
  проходит целый круг туда-обратно (на RU это 200–280 мс). Вход, отказывавший
  с «нет связи с сервером» в это окно, ругался на **живую** связь.
  `login()` / `register()` / `resume()` теперь ждут приветствия
  (`Net.is_greeted()`), а UI на это время пишет «подключение…».
* **Клиент не переключает сервер посреди партии.** Автопереподключение
  пробует **тот же** сервер. Отказ `game.rejoin` → событие `game_lost`.
* **Клиент не переподключается на коде закрытия 4001** (вход в другом окне).

### Вёрстка

* **`CenterContainer` + `ScrollContainer` = нулевая высота.** Не повторять.
  `MarginContainer` (на весь экран) → `ScrollContainer`.
* **Метка с автопереносом без ширины схлопывается до 1 px** и режет текст
  по символу. Нужен `size_flags_horizontal = SIZE_EXPAND_FILL`. В
  `CenterContainer` этого **не хватает**: контейнер отдаёт ребёнку
  минимум, а у метки с автопереносом он равен одному символу — строка
  рассыпается буква-в-букву. Нужен `custom_minimum_size.x` от ширины окна
  (см. `_fit_toast_width`).
* **Пустой контейнер без флагов схлопывается по ширине в ноль.** Флаги
  задаются сразу, на пустом.
* **Прокрутка пальцем начинается не везде.** `ScrollContainer` берёт жест,
  только если палец попал **мимо** всех `STOP`-контролов: пустой `VBox`
  внутри скролла глушит свайп целиком. Поэтому «пустые» контейнеры
  (списки комнат, страницы лобби, главное меню) — `MOUSE_FILTER_IGNORE`
  (`ScrollFix.relax`), а кнопки, поля, `RichTextLabel` в скролле и
  drop-цели остаются `STOP`. `relax()` **нельзя** вызывать там, где есть
  drop-цели: `DropLayer` обязан ловить касание.
  А кнопка или поле ввода **внутри** скролла — не тупик: жест, начатый на
  `KEEP`-контроле с скролл-предком, разбирает `ScrollDrag` в `_input`
  сцены раньше GUI. Дальше порога (10 px) это прокрутка — клик при этом
  подавлен; короткий тап отыгрывается событиями press+release, и кнопка
  срабатывает как обычно. Карточки, ряды и прочие drop-цели `ScrollDrag`
  не трогает — ими дальше решают `Game._input` и нативный `ScrollContainer`.
* **Drop-цель нельзя разжаловать в `PASS`/`IGNORE`:** жест с неё уходит в
  `ScrollContainer`, и карточки перестают в неё вставать. Для стола
  прокрутка по фону рядов разобрана вручную в `Game._input`: жест ловится
  там, прокрутка двигается напрямую, с карточки жест остаётся
  перетаскиванием.
* **Окно игры 576×1024, портрет.** Проверяйте вёрстку на нём: при 1024×1024
  влезает всё, а в настоящем окне ломается.

### Godot 4.7 — API

* `fit_content` и `placeholder_text` — **свойства**, не методы.
* `VERTICAL_ALIGNMENT_CENTER` / `HORIZONTAL_ALIGNMENT_CENTER` — **глобальные**
  константы. `Control.VERTICAL_ALIGNMENT_CENTER` **не существует**.
* У `X509Certificate` есть только `load`, `load_from_string`, `save`,
  `save_to_string`. Никаких `get_subject_string`.
* `ResourceLoader.exists("res://...pem")` — `false`. Для `.crt` — `true`.
* `ClassDB.class_has_property` **не существует**, свойства берутся из
  `ClassDB.class_get_property_list(cls, false)` — обязательно `false`,
  иначе не видно унаследованные (`visible` объявлен в `CanvasItem`).
* `WebSocketPeer` в 4.7 — только `connect_to_url`. `connect_to_socket` нет.
* Предупреждение `Unexpected NUL character` при работе с сертификатами
  **безобидно**: движок дописывает NUL-терминатор в `save_to_string()`.
  Содержимое совпадает с файлом байт в байт.

### Сервер

* **Партия в памяти.** Рестарт сервиса = партии потеряны. Аккаунты переживут.
* **`StartLimit*` живут в `[Unit]`**, а не в `[Service]`. Помещённые в
  `[Service]`, они молча игнорируются, и падающий в цикле сервер
  перезапускается бесконечно.
* **`ProtectSystem=strict` + `ReadWritePaths=/var/lib/digital-game`.** Без
  второй строки SQLite не может создать базу, и сервер падает на старте.
* **systemd молча игнорирует неизвестные ключи.** Поэтому юнит проверяется
  `systemd-analyze verify` **до** установки.
* **На RU 709 МБ RAM, свободно ~256 МБ, свопа нет.** Без `MemoryMax` ядро
  выберет жертву по размеру процесса — и это окажется nginx/xray с чужим
  продакшеном. `MemoryHigh=140M` / `MemoryMax=200M` / `MemorySwapMax=0`
  заставляют умереть наш node, а не чужой сервис.
* **`fs.existsSync` врёт** для существующего, но нечитаемого файла
  (EACCES на непроходимом родителе) — отдаёт `false`. Читать и ветвиться
  по `errno`.
* **В `index.js` есть защита на старте**: поле экземпляра, затевающее
  метод одноимённого класса, приводит к падению. Иначе такой конфликт
  молча ломает вызов.

### Репозиторий

* `.env` **не коммитится** (`.gitignore`). Перед `git add -A` стоит проверить,
  что он не попал в индекс.
* `server/deploy/tls/`, `*.key`, `*.pem` — не коммитятся.
* `certs/*.crt` — **коммитятся** и меняются только вместе с клиентом.
* `node_modules/` — не коммитится, восстанавливается из `package-lock.json`.

   Собрать, запустить **на другой машине** (не в редакторе) и зайти в сеть —
   единственная проверка, которая считается настоящей.
3. **Кнопка смены пароля.** `auth.password` работает на сервере и в
   `Net.change_password()`, интерфейса нет. Мелочь, но без неё
   скомпрометированный пароль нечем сменить.
4. **Показать соперникам «отвалился».** `GameState.connected` уже есть,
   стоит довести до интерфейса партии.

### Сервер

5. **Ограничить частоту запросов.** Сейчас ограничены `MAX_OPS_PER_COMMIT=64`
   и `MAX_MESSAGE_BYTES=256 КБ`, но не частота. Публичный IP без лимита на
   вход — это и словарь паролей, и забитый event loop.
6. **Просроченные логины.** `last_seen_ms` пишется, но не используется.

### Качество

7. **CI.** Сейчас его нет вообще, а набор тестов уже большой и требует

   `test_conformance`/`test_rules`/`test_protocol` снял бы главный источник

10. **Страховка от смены адресов.** Список серверов зашит в клиент, значит
    переезд сервера = релиз клиента. Стоит подумать, не отдавать ли адреса
    через gossip с самого начала (нужен хотя бы один зашитый адрес,
    чтобы достучаться до первого).

### Чего сознательно делать не надо

* **Реплицировать партии.** Синхронизация состояния партии между серверами
  дороже, чем её потеря. Если понадобится — смотреть в сторону
  «сервер присоединяется к партии», а не «партия мигрирует».
* **Ставить nginx на 443.** Там чужое продакшен-приложение. Наш порт — 6767.
* **Отключать проверку сертификата** («accept_invalid_certs»). При зашитом
  сертификате это не нужно, а при потере зашитого — значит клиент уехал
  неполным, и это надо чинить сборку, а не проверку.
* **Раздавать фишки ботов по сети.** Боты в сети играют (добор и подмена
  выбывших), но их рука, как и у людей, наружу уходит только числом фишек.
